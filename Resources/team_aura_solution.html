04 — Feature Architecture

What we build

M1 · MANDATORY

Folder Structure Analysis

Parse repository tree → run Gemini prompt per directory cluster → generate plain-English purpose for each folder. Color-coded by criticality (critical / support / test).

Output: Interactive tree with hover explanations
M2 · MANDATORY

Entry Point Detection

Heuristic scan for main.py, server.js, index.js, app.py etc. Parse imports/calls from entry file → build execution timeline as animated flow.

Output: Animated execution flow diagram
M3 · MANDATORY

Dependency Mapping

AST-based import extraction across all source files. Build a directed graph (route → controller → service → model). Render as interactive D3.js force graph — click to trace paths.

Output: Clickable D3 dependency graph
B1 · BONUS

Critical File Identification

Score files by import frequency + business logic density. Highlight the top 5 most impactful files with risk-color badges. Judges love this — it's visually dramatic.

B2 · BONUS

Execution Flow Tracer

Pick any API route → trace the full request lifecycle from HTTP handler → middleware → controller → service → DB. Renders as a horizontal swimlane diagram.

B3 · BONUS

AI Repository Summary

One Gemini call with the full context window: tech stack, architecture style (MVC / microservices / monolith), key design decisions, and code quality signals. The wow factor.

✦ CREATIVE BONUS — OUR DIFFERENTIATOR

Ask The Codebase — Conversational AI Panel

A live chat tab where developers type natural language questions: "Where is the authentication logic?", "What happens when a user resets their password?", "Which file should I edit to add a new API endpoint?" — answered by Gemini with RAG over the indexed codebase. This is the real onboarding killer feature. No other team will ship this in 10 hours.

⬡ NEW — SANDBOX TESTING PHASE

Automated Repo Validation Suite

Before any analysis output is shown to the user, the repo passes through a 4-stage sandbox: Intake → Sanitisation → Dry-Run Analysis → Confidence Scoring. Detects malicious files, empty repos, unsupported languages, and oversized clones. Outputs a health report card alongside every analysis — so judges see the system being responsible, not just fast.

Output: Green / Amber / Red sandbox health badge per repo

Users ask: "How do I add a private repo?", "Why is my dependency graph empty?", "What does the red badge mean?" — answered instantly by a Gemini-powered support agent with knowledge of our own system. 08 — Sandbox Testing Phase

Every repo goes through the
gauntlet before it gets analysed.

No raw input hits the Gemini API. The sandbox is a pre-analysis pipeline that validates, sanitises, and confidence-scores every repository — catching bad inputs before they waste API calls or crash the demo.

STAGE 01
Intake & Size Check
Clone repo with depth=1. Count files. Reject if >5,000 files or >500MB. Flag private repos. Detect empty repos.
AUTO-GATE
STAGE 02
Sanitisation
Scan for binary blobs, suspicious scripts, symlink loops. Strip files outside analysis scope. Ignore node_modules, .git, dist, build.
SECURITY
STAGE 03
Dry-Run Analysis
Detect language distribution. Attempt entry point detection. Check AST parsability on 5 sample files. Estimate analysis time.
PRE-FLIGHT
STAGE 04
Health Score
Emit Green / Amber / Red badge. Green = full analysis. Amber = partial (large repo, mixed languages). Red = blocked.
VERDICT
✓ What passes sandbox (Green)
✓ Repo under 5,000 files
✓ Detectable language (JS / Python / Java / Go / Ruby)
✓ At least one parsable entry point candidate found
✓ AST extraction succeeds on 3+ sample files
✓ No binary-only directories at root level
✓ Clone completes in under 30 seconds
⚠ What triggers Amber warning
⚠ Mixed-language repo (>3 primary languages)
⚠ 1,000–5,000 files (analysis capped at top 500 by score)
⚠ Minified JS files detected (stripped from AST pass)
⚠ No clear entry point (best-guess flagged)
✗ What gets blocked (Red)
✗ Repo over 5,000 files — reject with clear error
✗ Zero source files after sanitisation
✗ Clone timeout (>60s) — shallow clone failed
Why this matters for judges

When a judge pastes an unknown repo, they see a live sandbox progress bar running through 4 stages before results appear. It signals engineering maturity — we're not just piping raw input to an LLM and hoping for the best. The health badge stays visible on every tab throughout the session.

12 — Risk Register

Know before you go

HIGH
RAG pipeline takes too long to build. Mitigation: Build Ask AI last. If it's not ready, demo M1+M2+M3+B3 summary without it. Still competitive.
HIGH
Judge's mystery repo uses an unexpected language. Mitigation: Add Ruby + Go entry point heuristics early. Fallback: file extension detection + Gemini analysis still works.
MED
Gemini API rate limits during demo. Mitigation: Cache all analysis results after first run. Demo repos are pre-cached before presentation.
MED
Large repos take too long to clone + analyse. Mitigation: Cap at 1000 files. Shallow clone (depth=1). Show progress bar so judges see it working, not frozen.
LOW
Sandbox flags a judge's repo as Amber. Mitigation: Amber still produces full analysis — it just shows a warning badge. This actually demonstrates the sandbox working as intended. Frame it as a feature.
LOW
AuraBot gives a wrong answer about the tool. Mitigation: System prompt is fully controlled by us. Write 20 Q&A pairs covering every likely question and include them verbatim in the prompt. Test before demo.
